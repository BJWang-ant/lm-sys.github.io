## TL;DR

On four H20-3e GPUs, one SGLang worker can use context parallelism for long prompts and split query rows across ranks during decode. We use that colocated worker to measure eight changes cumulatively, from FP8 Indexer scoring to MoE sharding. We also provide a single-host disaggregated launch with four GPUs per role.

At concurrency 24, the final retained colocated configuration reduced mean end-to-end latency from **9.97 s to 7.96 s (20.17%)** and increased output throughput from **1,184.7 to 1,482.7 tokens/s (25.15%)**. Both runs completed 256 requests with nominal 65,536-token inputs, 500 output tokens, and a 93.75% shared prefix. Mean TTFT rose from 2.09 s to 2.40 s while mean TPOT fell from 15.79 to 11.13 ms per output token.

On eight H20-3e GPUs split 4P+4D, the final retained configuration reduced mean end-to-end latency from **13.63 s to 4.69 s (65.57%)** and increased output throughput from **846.8 to 2,446.2 tokens/s (188.89%)**. The split baseline uses the earlier BF16 Torch prefill scorer. The colocated baseline uses the original shape-based scorer.

## Start with a Four-GPU Worker

DeepSeek-V4.1-Flash uses compressed attention and Indexer layers that share candidate blocks. A source layer publishes blocks worth searching, and later consumers select from those blocks. With decoder-side sliding-window bounded replay, prefill also processes fewer rows in the later layers. The workload therefore combines large prefill score tiles, small tail tiles, and short decode verification batches. [DeepSeek-V4.1 architecture and serving overview](/blog/2026-09-10-deepseek-v41/).

The colocated baseline runs interleaved prefill CP on TP4 with expert sharding across four GPUs. Decode attention starts in TP mode. The worker keeps its per-rank Engram tables in host memory to leave device memory for the weights, FP8 E4M3 KV cache, and scratch buffers. All colocated rows use Humming with FP8 inputs, an 8,192-token prefill chunk and admission budget, 0.80 static memory fraction, and a 64-request running limit. They use hierarchical caching with a 2× host tier and write-through policy. Bounded replay, a decode graph limit of 64, and the bundled DSpark draft with block size five are fixed across the sweep.

The 93.75% prefix fraction describes how the benchmark constructs requests. After tokenization the baseline averaged 67,002 input tokens per request and reported a 93.21% cache-hit rate. We count a run only when all 256 requests succeed and generate all 128,000 output tokens.

## The Colocated Sweep

Each trial adds one change to the last retained configuration. We keep a trial when mean end-to-end latency decreases or output throughput increases. When neither improves, the next trial uses the same control. The colocated CP baseline uses the `auto` prefill scorer, which selects DeepGEMM for sufficiently large query tiles and the Triton FP8 scorer for smaller tiles. Its other settings are eager prefill, BF16 decode scoring, independent verify queries, the unfused selection path, EP4, and the smaller scoring budgets. A separate TP4 baseline uses the same workload with DSpark and runs after the CP sweep.

| Stage | Change | Control for the comparison |
| --- | --- | --- |
| 0 | Colocated baseline | Settings above |
| 1 | Force DeepGEMM FP8 for prefill Indexer scoring | Shape-based prefill scoring |
| 2 | Breakable CUDA graphs for prefill | Eager prefill |
| 3 | FP8 decode Indexer dot products | BF16 decode Indexer dot products |
| 4 | Reuse BF16 paged Indexer K tiles during verification | Independent K loads per query |
| 5 | Fuse prefill top-k writeback and block selection | Unfused selection |

| 7 | Increase prefill and decode score-buffer budgets | 64 MiB and 128 MiB, respectively |

For each stage we record mean TTFT, TPOT, and end-to-end latency, p99 end-to-end latency, aggregate output tokens per second, and observed cache hit rate. We calculate latency reductions as `1 - new / old` and throughput changes as `new / old - 1`. Stage deltas use the retained control as the denominator. The total compares the final retained configuration with stage 0.

### 1. Force DeepGEMM for All Prefill Indexer Layers

Gather each request's packed FP4 Indexer keys once, apply their block scales during conversion to FP8, and use `deep_gemm.fp8_mqa_logits` on the gathered keys and FP8 queries. The DeepGEMM call emits FP32 logits, with the causal tail masked for selection. We set the Hopper scorer to `deepgemm` for full scoring, candidate publishers, and candidate consumers, including the short tail shapes. Consumers still restrict the final selection to the published blocks.

The earlier profile showed that DeepGEMM shortened large scoring tiles. Small tail tiles and consumers have a different tradeoff because a dense DeepGEMM score can do more work than a compact score. The forced-scoring row measures that tradeoff end to end.

At concurrency 24, forced DeepGEMM reduced mean end-to-end latency by 2.86% and increased output throughput by 3.76%. Mean TTFT increased from 2.09 s to 3.38 s, and p99 end-to-end latency increased from 17.15 s to 17.46 s. Mean TPOT fell from 15.79 to 12.62 ms per output token.

### 2. Replay Prefill with Breakable CUDA Graphs

Breakable CUDA graphs capture stretches of GPU work between operations that need eager execution. Replaying those stretches reduces CPU launches and gaps between ranks. On this Hopper path, the Indexer and compressor can continue to run eagerly. Bounded replay also needs graph buckets sized for the live decoder tail. Replaying a short tail in a large full-prompt bucket can add enough attention and MoE work to offset the launch savings.

In an earlier DeepSeek-V4-Flash experiment, C4 Indexer scratch scaled with the model's maximum context. Context buckets bounded the scratch width during capture. Reported peak capture allocation fell from 43 GB to 18 GB for a 16,384-token bucket and from 22 GB to 10 GB for an 8,192-token bucket. These are capture allocations from the earlier model. [Merged SGLang PR #36534](https://github.com/sgl-project/sglang/pull/36534).

### 3. Use FP8 Dot Products in the Decode Indexer

The paged scorer reads the FP4 key payload and its block exponents together. It converts suitable operands to FP8 inside the kernel and uses FP8 Tensor Core dot products. It retains the reference BF16 rounding stages after the dot and repairs tiles in BF16 when the operands exceed the supported FP8 range.

In one earlier colocated trace, an Indexer kernel went from 476 to 181 μs. End-to-end latency also includes attention, MoE, speculative acceptance, and scheduling, so the serving experiment measures the exposed fraction of that kernel gain.

In the matched sweep, mean TPOT fell from 14.17 to 13.63 ms per output token. Mean E2E latency rose by 4.91% and throughput fell by 4.78%, so subsequent trials used BF16 decode scoring.

### 4. Reuse Paged Indexer K Tiles During Verify

During DSpark target verification, consecutive queries from the same request share most of their visible keys. The original layout loaded and dequantized a tile for each query. The grouped layout shares that K tile across multiple same-request query rows and applies each row's own causal limit. It uses full-request groups or aligned pairs when the layout permits.

In the earlier split-worker FP8 profile, the full scorer and candidate publisher each dropped from about 300 to 210 μs per call. The candidate consumer follows a separate compact path. The BF16 variant in this sweep shares the two dequantized K halves across rows and preserves the per-row dot and reduction order. We checked its visible logits and published block scores against independent rows on H20, including CUDA Graph replay.

### 5. Fuse Prefill Selection and Writeback

After top-k, the worker has to filter invalid picks, put the remaining positions in order, and translate logical positions to physical KV slots. One Triton kernel combines these steps in `write_prefill`. A second Triton path replaces the sequence that masks scores, reduces them to block maxima, and selects candidate block IDs for downstream layers.

In the split-worker traces, the writeback region went from about 150 to 43 μs per score chunk, and candidate-block selection went from about 1.7 to 0.4 ms. Both changes are enabled together in the colocated sweep.

### 6. Shard Each Expert Across TP Ranks

With EP4, each rank owns a subset of experts. Uneven routing can leave early ranks waiting for the busiest rank at the output collective. With EP1 on TP4, each rank instead holds a shard of each expert's intermediate weights, spreading hot experts across the ranks.

The earlier split-worker trace recorded a prefill forward reduction from about 770 to 650 ms while the expert GEMMs themselves took longer. The change trades compute shape against collective waiting. Its benefit depends on the routing distribution and batch shape.

### 7. Increase Indexer Score Budgets

The prefill scorer builds FP32 score tiles and caps their query rows using the score width and a memory budget. The decode candidate scorer also reserves space for block maxima and selection scratch. We raise those budgets from 64 MiB to 2 GiB for Hopper prefill and from 128 to 512 MiB for compact decode. With a long context, larger tiles reduce how often scoring and selection repeat. The worker still admits at most 8,192 prefill tokens per chunk.

### 8. Keep Prefill CP and Split Decode Query Rows

Interleaved CP distributes the prompt rows. During target decode and verify, the optimized attention path divides query rows across the same four ranks and lets each rank use its full attention heads. The compressor still updates replicated KV and Indexer state, and the attention outputs are gathered back into batch order. DSpark draft attention stays in TP mode. The worker keeps one scheduler, so the change can reduce per-rank attention and Indexer work without moving requests between server replicas. [SGLang PR #45729](https://github.com/sgl-project/sglang/pull/45729).

## Disaggregated Serving

The split sweep uses one prefill worker on GPUs 0–3 and one decode worker on GPUs 4–7. Every row uses an 8,192-token prefill chunk, a 0.25× hierarchical host cache on prefill, and DSpark with Humming on both workers. Static memory fractions are 0.80 for prefill and 0.85 for decode. Decode has a 256-request running limit. The router sends requests to prefill first and decode continues from the state transferred over Mooncake's intra-node NVLink path.

The split baseline uses TP4 attention and EP4 on both roles, with the same 256 prompts, concurrency 24, and 500-token outputs as the colocated sweep. Its prefill Indexer uses the earlier BF16 Torch path, with dense per-request scores and the Torch head-score reduction. The DeepGEMM trial switches every prefill Indexer layer to `deep_gemm.fp8_mqa_logits`. Both fixed paths bypass the Triton FP8 prefill scorer. The trials apply the same retention rule as the colocated sweep. Each split result uses eight GPUs, four per role, so we calculate its gains against the eight-GPU split baseline.

| Stage | Split-worker trial |
| --- | --- |
| 0 | TP4 prefill and TP4 decode baseline |
| 1 | Interleaved CP4 prefill and DP4 decode attention with DP LM head |
| 2 | DeepGEMM FP8 prefill scoring |
| 3 | Breakable prefill CUDA graphs |
| 4 | TP MoE on both workers |
| 5 | Larger prefill score budget |
| 6 | Triton prefill selection and writeback |
| 7 | Paged BF16 K-tile reuse |
| 8 | One Mooncake NVLink submission for a chunk's KV layers |
| 9 | Wait briefly for final KV transfer completion before polling |

Interleaved CP spreads each prefill chunk's query rows across the four prefill ranks. Decode runs data-parallel attention with a DP LM head, so ranks process different requests.

The NVLink trial combines one chunk's KV layer copies in one submission to reduce CPU submission work. [SGLang PR #38984](https://github.com/sgl-project/sglang/pull/38984).

The polling trial lets newly sent final chunks finish for up to 5 ms before the scheduler performs its regular rank-consensus poll. Transfer completion or failure can wake the wait early. This can save a scheduler round when the final copy is about to finish, at the cost of holding the prefill scheduler briefly when it takes longer.

We developed the paged K-tile reuse, prefill selection fusion, and score-budget changes in the split-worker experiments. The colocated sweep measures them again because the GPU allocation, batching, and cache behavior differ. An earlier split experiment also tried batching KV transfers across requests. Its traces showed little queue buildup and few opportunities to batch, with no clear end-to-end gain on that workload. [SGLang PR #43995](https://github.com/sgl-project/sglang/pull/43995).

All split rows completed 256 requests and 128,000 output tokens. Each row represents one timed run. Moving to prefill CP and decode DP cut mean TTFT from 12.04 to 5.16 s. Switching to DeepGEMM cut it further to 2.66 s and increased output throughput by 43.11% over the CP/DP control.

NVLink layer batching reduced mean TTFT but left mean E2E slightly higher and output throughput 1.63% lower. The polling trial therefore compared with stage 7. It kept the original layer submissions and reduced mean E2E by 12.41 ms while output throughput fell 1.37%. Stage 7 had the highest output throughput at 2,480.23 tokens/s. Stage 9 had the lowest mean E2E and was retained under the sweep rule.

The `pd0` through `pd9` modes use the 4P+4D launcher described above. The script waits for both workers, starts the router, and waits for the router to report readiness before sending benchmark traffic. The summary script reports split results separately from the four-GPU colocated runs.

## Reproduce the Runs

Use SGLang revision `91afc4f363cc60ca0bf98d38e87cc6cfa32062fe` from the `v4.1/h20-dev-pd-blog` experiment branch for the split sweep. This revision restores the dense BF16 scoring, unpadded K width, and unfused head-score reduction when `SGLANG_DSV41_TORCH_PREFILL_INDEXER=1`. The launcher uses this setting for the split baseline and sets it to zero for the all-layer DeepGEMM trial. It fixes `SGLANG_DSV41_SM90_PREFILL_INDEXER=deepgemm` throughout the split sweep, so a retained DeepGEMM trial continues to use that scorer for all query tile sizes.

Colocated stages 0–3 used `0a62348472347e4f712786f68b3c18031189b6a7`, and the later colocated rows used `78be0635d7baf0da911537c68a5d61aa2f909cfe`, which adds opt-in BF16 tile reuse and controls for the split-worker trials. These colocated measurements retain their original `auto` control. Exact reproduction requires access to these experiment revisions. The public PRs above cover individual pieces of the stack.

The environment uses Python 3.12, PyTorch 2.14.1 with CUDA 13.0, Triton 3.8.0, Humming kernels 0.1.12, and `sgl-deep-gemm` 0.2.2+sm90w4a8. The test host uses NVIDIA driver 570.133.20 with the CUDA compatibility libraries loaded by the serving shell. The split launch uses `sglang-router` 0.3.2 and `mooncake-transfer-engine-cuda13` 0.3.10.post2. Point `MODEL_PATH` at one local DeepSeek-V4.1-Flash checkpoint for every row, including its bundled DSpark draft.

Download the [launch and benchmark script](/repro/deepseek-v41-h20/run.sh) and the [results summarizer](/repro/deepseek-v41-h20/summarize.py). Run them from the checked-out SGLang repository in the serving environment.

```bash
export MODEL_PATH=/path/to/DeepSeek-V4.1-Flash
export DATASET_PATH=/path/to/ShareGPT_V3_unfiltered_cleaned_split.json
export LOG_ROOT="$PWD/h20-v41-results"
export CONCURRENCIES=24
bash /path/to/run.sh 0 1 2 3 4 5 6 7 8 colocate-tp
bash /path/to/run.sh pd0 pd1 pd2 pd3 pd4 pd5 pd6 pd7 pd8 pd9
python3 /path/to/summarize.py "$LOG_ROOT" --concurrency 24
```

The dataset argument is carried over from the original client command. The generated shared-prefix loader synthesizes the requests from the tokenizer and seed. The script starts a fresh worker for each stage, waits for readiness, and writes the expanded commands and JSONL results in separate directories. Use `--dry-run` to inspect those commands. Set `CONCURRENCIES="64 32 24 16 8"` for the broader load sweep with the same protocol.
